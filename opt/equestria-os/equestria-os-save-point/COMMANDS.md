# equestria-os-save-point — команды и действия GUI

Самый «системный» из GUI-инструментов: работает и как обычное приложение, и как pacman-хук + systemd-таймер + аварийный авто-откат при неудачной загрузке.

## Выбор бэкенда (`detect_backend()`, `backend.py:119-135`)

1. **Btrfs** (`BtrfsBackend`, `backend.py:224`) — если корень (`/`) на Btrfs и есть `btrfs-progs`. Причина выбора именно Btrfs первым: у неё снапшоты — это встроенная возможность самой файловой системы (copy-on-write — при записи меняется не сам блок данных, а создаётся новая версия, старая остаётся доступна через снапшот), поэтому создание снапшота происходит мгновенно и не занимает лишнего места, пока файлы не начнут реально меняться.
2. **Restic** (`ResticBackend`, `backend.py:355`) — во всех остальных случаях (ext4/xfs/…), у которых нет собственного механизма снапшотов на уровне ФС. Restic — сторонняя программа резервного копирования с **дедупликацией по чанкам** (файл режется на куски, одинаковые куски между разными снапшотами хранятся один раз) и сжатием. Репозиторий — в `/var/lib/equestria-save-point/restic-repo`, ключ шифрования — в `repo.key` (генерируется `openssl rand -base64 32` — 32 случайных байта в кодировке base64, стандартный способ получить криптостойкий пароль).
3. **Timeshift** — фолбэк, если ни то ни другое не подходит, но `timeshift` установлен (использует `rsync` — построчное копирование файлов, самый простой, но и самый медленный/тяжёлый по месту вариант).

### Объяснение команд по бэкендам

> **`btrfs subvolume snapshot -r / <путь>`** — `subvolume` в Btrfs — это как бы «раздел внутри раздела», у которого можно снять снимок независимо от остального диска. `-r` — снапшот **read-only** (защита от случайной правки самой точки восстановления после её создания). Корневой `/` в Btrfs-системах Arch по умолчанию сам является subvolume (обычно называется `@`), поэтому его можно снапшотить целиком одной командой.
>
> **`btrfs subvolume delete <путь>`** — в отличие от `rm -rf`, это не рекурсивное удаление файлов один за другим, а операция на уровне метаданных Btrfs — снапшот просто перестаёт существовать как отдельная сущность, освобождая место, которое реально занимали только его уникальные (не общие с текущей системой) данные.
>
> **`restic backup / --exclude=<путь> ... --tag <тег> --compression auto`** — `restic` сканирует указанный путь (`/`), режет файлы на куски (chunking), сохраняет только новые/изменившиеся куски со времени прошлого снапшота того же репозитория. `--exclude` можно указывать многократно — список того, что не нужно бэкапить (`RESTIC_EXCLUDES`, `backend.py:18-56`: виртуальные ФС `/proc`/`/sys`/`/dev`, кеш пакетов, `/home` — личные файлы намеренно исключены, это НЕ бэкап документов, а именно снимок состояния системы). `--tag` — метка снапшота (используется потом, чтобы найти/защитить конкретный снапшот по имени, а не по случайному ID). `--compression auto` — restic сам решает, сжимать ли конкретный кусок данных (уже сжатые файлы вроде `.zip` сжимать повторно бессмысленно).
>
> **`restic forget --keep-last N --keep-tag daily-protected --prune`** — `forget` помечает старые снапшоты как «больше не нужны» по правилу (тут: оставить последние N обычных, но никогда не трогать снапшоты с тегом `daily-protected`), `--prune` заставляет сразу же физически освободить место (без этого флага `forget` только убирает снапшот из списка, а данные могут остаться, если на них ссылаются другие снапшоты — освобождение места отдельная, более медленная операция).
>
> **Восстановление на Btrfs** (`restore_cmd()`, `backend.py:293-313`) — самое сложное место: временно монтирует настоящий корневой subvolume (не `/`, а его «родитель» на диске) во временный каталог через `mount -o subvol=/`, снимает копию нужного снапшота поверх текущего корня, а **старый** текущий корень переименовывает в `<subvol>_old_<timestamp>` вместо удаления — так что если откат оказался неудачным решением, старую систему всегда можно найти на диске и вернуть вручную. Требует **перезагрузки**, потому что уже запущенное ядро продолжает использовать старые файлы из памяти, подмена на диске не меняет то, что уже загружено и выполняется.
>
> **Restic restore** перезаписывает файлы **немедленно** прямо в работающей системе — рискованнее в моменте (можно перетереть файл, который в этот момент использует запущенная программа), но не требует перезагрузки, потому что не подменяет весь корень целиком, а просто копирует файлы поверх.

Каждый клик «Создать снапшот» в GUI сначала делает **скриншот рабочего стола** (`take_screenshot()`, `screenshot.py:12-...`: пробует `spectacle` → `grim` → `scrot` → `import` — четыре разных инструмента для скриншотов, потому что каждый работает только в своём окружении: `spectacle` — родной для KDE, `grim` — для чисто Wayland-композиторов без KDE, `scrot`/`import` — для X11 без KDE), конвертирует в `.webp` (современный формат с хорошим сжатием), кладёт в `~/.cache/equestria-os-save-point/screenshots/<timestamp>.webp`.

## Автоматические снапшоты — отдельная система, работает даже если GUI никогда не открывали

* **`/etc/pacman.d/hooks/equestria-save-point.hook`** — pacman-хук: файл-описание, который сам pacman читает перед/после установки пакетов (это встроенный механизм pacman, не что-то, что проект придумал с нуля). `When = PreTransaction` — сработает **до** начала установки/обновления/удаления пакета, запускает `pacman-snapshot.sh auto:pacman` от имени root (pacman и так работает от root, дополнительный `pkexec` не нужен).
* **`/etc/profile.d/60-equestria-save-point.sh`** — файлы в `/etc/profile.d/` автоматически подгружаются в каждый login-шелл (это стандартный механизм, которым дистрибутивы настраивают переменные окружения при входе). Здесь он переопределяет bash-функцию `flatpak`, оборачивающую настоящую команду: на `install/update/upgrade/uninstall/remove` в фоне запускает `pkexec pacman-snapshot.sh auto:flatpak`, не блокируя саму команду flatpak.
* **`equestria-save-point-daily.timer`** (`OnCalendar=daily` — синтаксис systemd-таймеров для «раз в календарные сутки») → `equestria-save-point-daily.service` → `pacman-snapshot.sh D` — ежедневный «защищённый» снапшот (тег `daily-protected`/`D`), идемпотентно (проверяет по дате в имени файла, не создаст второй за тот же день), хранится отдельно от обычных и не удаляется при обычной чистке (`--keep-tag daily-protected` у Restic, отдельная папка `daily/` у Btrfs); хранится последние 7 штук.
* `pacman-snapshot.sh` сам определяет бэкенд по `/proc/mounts` (Btrfs vs Restic) — не зависит от GUI-процесса, может работать даже если GUI ни разу не запускали.
* Лимит хранения для автоматических снапшотов читается из `/var/lib/equestria-save-point/hook-config` (просто число, по умолчанию 10) — **не** из пользовательского `~/.config/equestria-save-point/config.json`, который использует только GUI для ручной очистки. Эти два значения синхронизируются только через диалог настроек (см. ниже).

## Диалог настроек → «Применить» (`_apply_hook_settings()` → `hooks.build_hook_apply_script()`, `hooks.py:19-58`)

Один `pkexec bash -c "<script>"`, который разом:
* пишет лимит хранения в `/var/lib/equestria-save-point/hook-config`;
* если репозиторий Restic был перенесён в другое место — `mv` старого репозитория и запись нового пути в `/var/lib/equestria-save-point/repo-path` (или `rm -f` этого файла, если путь снова дефолтный);
* включает/выключает pacman-хук: `cp`/`rm -f` файла `equestria-save-point.hook` в `/etc/pacman.d/hooks/`;
* включает/выключает flatpak-обёртку: `cp`/`rm -f` файла `flatpak-hook.sh` в `/etc/profile.d/60-equestria-save-point.sh`.

## ⚠ Автоматический аварийный откат при неудачной загрузке

* `/usr/lib/systemd/system/graphical.target.d/auto-restore.conf` — **drop-in** (файл-дополнение к существующему systemd-юниту без правки самого оригинала — механизм `.d`-каталогов systemd) на `graphical.target` (цель, которую systemd считает достигнутой, когда графическая сессия успешно поднялась) с `OnFailure=equestria-auto-restore.service` — если systemd решит, что до `graphical.target` дойти не удалось, автоматически запускается:
* **`equestria-auto-restore.service`** → `auto-restore.py` → берёт **самый свежий** снапшот (без выбора, без подтверждения) и вызывает его `restore_cmd()`, затем **`ExecStartPost=systemctl reboot --force`** — принудительная перезагрузка сразу после отката (`--force` пропускает обычные проверки systemd перед релогином, немедленный ребут).
* Это полностью автоматический процесс без участия пользователя — если недавний снапшот сам был сделан с проблемой (например, сразу перед поломкой), система всё равно откатится на него и перезагрузится.

## `restore-system` — CLI для восстановления без GUI (`/usr/bin/restore-system` → `restore-system.py`)

```
sudo restore-system            # список всех точек с ID и датой
sudo restore-system latest     # восстановить самую свежую
sudo restore-system day        # восстановить последнюю daily-protected (тег D)
sudo restore-system <ID>       # восстановить конкретную точку по ID
```

Требует root (проверяет `os.geteuid() != 0` сам, а не полагается на `sudo`/`pkexec` обёртку). Использует тот же `backend.restore_cmd()`, что и GUI.

# equestria-os-save-point — команды и действия GUI

Самый «системный» из GUI-инструментов: работает и как обычное приложение, и как pacman-хук + systemd-таймер + аварийный авто-откат при неудачной загрузке.

## Бэкенд: только Btrfs (`detect_backend()`, `backend.py`)

> **Поддержка ext4 и других файловых систем удалена (1.5.0, 2026-11) из-за нестабильности бэкапов.** Раньше на не-Btrfs корне работал Restic (а запасным — Timeshift): pacman-хук перед **каждой** транзакцией заново сканировал всю систему (`restic backup /`), из-за чего установка пакетов сильно замедлялась, а восстановление записывало файлы поверх работающей системы и получалось ненадёжным.

`detect_backend()` возвращает:
* `"btrfs"` — корень (`/`) на Btrfs и есть `btrfs-progs` → `BtrfsBackend`. Снапшоты — встроенная возможность самой файловой системы (copy-on-write — при записи меняется не сам блок данных, а создаётся новая версия, старая остаётся доступна через снапшот), поэтому создание снапшота происходит мгновенно и не занимает лишнего места, пока файлы не начнут реально меняться.
* `"unsupported"` — корень не на Btrfs (ext4/xfs/…). GUI показывает окно «Только Btrfs» с объяснением и блокирует «Создать»; `pacman-snapshot.sh` пишет одну строку и сразу выходит, не задерживая pacman.
* `"none"` — корень на Btrfs, но нет `btrfs-progs` (в пакете он в `depends`, так что это только при ручном удалении).

Старый репозиторий Restic (`/var/lib/equestria-save-point/restic-repo` + `repo.key`) приложение больше не трогает; при обновлении пакета `.install` подсказывает, как его удалить вручную.

## Действия в GUI → команды бэкенда (все идут через `pkexec bash -c "<cmd>"`)

| Кнопка | Backend-метод | Команда |
|---|---|---|
| **Создать точку** | `create_cmd()` | `mkdir -p <snap_dir> && btrfs subvolume snapshot -r / <snap_dir>/<timestamp>` |
| **Восстановить** | `restore_cmd(id)` | См. подробный разбор ниже |
| **Удалить точку(и)** | `delete_cmd()`/`delete_multiple_cmd()` | `btrfs subvolume delete <path>` |
| **Очистить старые** | `build_prune_cmd()` | Удаляет старые subvolume сверх лимита |

### Объяснение команд

> **`btrfs subvolume snapshot -r / <путь>`** — `subvolume` в Btrfs — это как бы «раздел внутри раздела», у которого можно снять снимок независимо от остального диска. `-r` — снапшот **read-only** (защита от случайной правки самой точки восстановления после её создания). Корневой `/` в Btrfs-системах Arch по умолчанию сам является subvolume (обычно называется `@`), поэтому его можно снапшотить целиком одной командой.
>
> **`btrfs subvolume delete <путь>`** — в отличие от `rm -rf`, это не рекурсивное удаление файлов один за другим, а операция на уровне метаданных Btrfs — снапшот просто перестаёт существовать как отдельная сущность, освобождая место, которое реально занимали только его уникальные (не общие с текущей системой) данные.
>
> **Восстановление на Btrfs** (`restore_cmd()`, `backend.py:293-313`) — самое сложное место: временно монтирует настоящий корневой subvolume (не `/`, а его «родитель» на диске) во временный каталог через `mount -o subvol=/`, снимает копию нужного снапшота поверх текущего корня, а **старый** текущий корень переименовывает в `<subvol>_old_<timestamp>` вместо удаления — так что если откат оказался неудачным решением, старую систему всегда можно найти на диске и вернуть вручную. Требует **перезагрузки**, потому что уже запущенное ядро продолжает использовать старые файлы из памяти, подмена на диске не меняет то, что уже загружено и выполняется.

Каждый клик «Создать снапшот» в GUI сначала делает **скриншот рабочего стола** (`take_screenshot()`, `screenshot.py:12-...`: пробует `spectacle` → `grim` → `scrot` → `import` — четыре разных инструмента для скриншотов, потому что каждый работает только в своём окружении: `spectacle` — родной для KDE, `grim` — для чисто Wayland-композиторов без KDE, `scrot`/`import` — для X11 без KDE), конвертирует в `.webp` (современный формат с хорошим сжатием), кладёт в `~/.cache/equestria-os-save-point/screenshots/<timestamp>.webp`.

## Автоматические снапшоты — отдельная система, работает даже если GUI никогда не открывали

* **`/etc/pacman.d/hooks/equestria-save-point.hook`** — pacman-хук: файл-описание, который сам pacman читает перед/после установки пакетов (это встроенный механизм pacman, не что-то, что проект придумал с нуля). `When = PreTransaction` — сработает **до** начала установки/обновления/удаления пакета, запускает `pacman-snapshot.sh auto:pacman` от имени root (pacman и так работает от root, дополнительный `pkexec` не нужен).
* **`/etc/profile.d/60-equestria-save-point.sh`** — файлы в `/etc/profile.d/` автоматически подгружаются в каждый login-шелл (это стандартный механизм, которым дистрибутивы настраивают переменные окружения при входе). Здесь он переопределяет bash-функцию `flatpak`, оборачивающую настоящую команду: на `install/update/upgrade/uninstall/remove` в фоне запускает `pkexec pacman-snapshot.sh auto:flatpak`, не блокируя саму команду flatpak.
* **`equestria-save-point-daily.timer`** (`OnCalendar=daily` — синтаксис systemd-таймеров для «раз в календарные сутки») → `equestria-save-point-daily.service` → `pacman-snapshot.sh D` — ежедневный «защищённый» снапшот (тег `P`), идемпотентно (проверяет по дате в имени файла, не создаст второй за тот же день), хранится отдельно от обычных и не удаляется при обычной чистке (отдельная папка `/.snapshots/daily/`); хранится последние 7 штук.
* `pacman-snapshot.sh` сам проверяет ФС корня по `/proc/mounts`: на Btrfs делает снапшот, на любой другой ФС сразу выходит с кодом 0 (транзакцию не блокирует). Не зависит от GUI-процесса.
* Лимит хранения для автоматических снапшотов читается из `/var/lib/equestria-save-point/hook-config` (просто число, по умолчанию 10) — **не** из пользовательского `~/.config/equestria-save-point/config.json`, который использует только GUI для ручной очистки. Эти два значения синхронизируются только через диалог настроек (см. ниже).

## Диалог настроек → «Применить» (`_apply_hook_settings()` → `hooks.build_hook_apply_script()`, `hooks.py`)

Один `pkexec bash -c "<script>"`, который разом:
* пишет лимит хранения в `/var/lib/equestria-save-point/hook-config`;
* включает/выключает pacman-хук: `cp`/`rm -f` файла `equestria-save-point.hook` в `/etc/pacman.d/hooks/`;
* включает/выключает flatpak-обёртку: `cp`/`rm -f` файла `flatpak-hook.sh` в `/etc/profile.d/60-equestria-save-point.sh`.

## Автоматического отката нет (убран в 1.5.0-3)

Раньше `graphical.target.d/auto-restore.conf` (`OnFailure=`) при неудачной загрузке запускал
`equestria-auto-restore.service`: последний снимок восстанавливался без спроса, затем
`systemctl reboot --force`. Это сломало пакеты KDE (2026-11), поэтому служба, drop-in и
`auto-restore.py` удалены. Восстановление — только вручную: кнопка в окне или `restore-system`.

## `restore-system` — CLI для восстановления без GUI (`/usr/bin/restore-system` → `restore-system.py`)

```
sudo restore-system            # список всех точек с ID и датой
sudo restore-system latest     # восстановить самую свежую
sudo restore-system day        # восстановить последнюю ежедневную защищённую
sudo restore-system <ID>       # восстановить конкретную точку по ID
```

Требует root (проверяет `os.geteuid() != 0` сам, а не полагается на `sudo`/`pkexec` обёртку). Использует тот же `backend.restore_cmd()`, что и GUI.

## Прочее

* Скриншоты — не сама точка сохранения, а просто превью для интерфейса; отсутствие подходящей утилиты для скриншота не мешает созданию снапшота, просто превью не будет.
* `test_fstab_parse.py` в других пакетах и юнит-тесты здесь не относятся к рантайму — не часть того, что реально выполняется у пользователя.
